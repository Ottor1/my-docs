# API 参考

以下接口仅用于文档展示，不提供真实服务。GitHub Pages 托管的是静态网页，在本站访问 `/api/docs` 不会得到下面的 JSON。

## 我为什么选择这个示例

这个网站有首页、关于、使用指南和 API 参考四页。我把“查询文档列表”作为接口练习，让返回条目与网站的实际页面对应，便于检查标题、路径和总数是否一致。

我希望通过这个例子练习把一个功能说明完整：调用者如何传参数、结果如何表示、参数无效时会得到什么信息。接口字段的设计也能反过来帮助我梳理网站的信息结构。

## 查询文档列表

| 项目 | 说明 |
| --- | --- |
| 请求方法 | `GET` |
| 请求路径 | `/api/docs` |
| 功能 | 按页返回文档条目列表 |
| 响应类型 | `application/json` |

### 查询参数

| 参数 | 类型 | 必填 | 默认值 | 约束 |
| --- | --- | --- | --- | --- |
| `page` | integer | 否 | `1` | 大于或等于 1 |
| `page_size` | integer | 否 | `10` | 1 到 100 |

请求示例：

```http
GET /api/docs?page=1&page_size=10 HTTP/1.1
Host: api.example.com
Accept: application/json
```

`api.example.com` 是说明用的示例域名，此代码块不代表可调用的在线服务。

### 成功响应示例

状态码：`200 OK`。

```json
{
  "items": [
    {"id": 1, "title": "首页", "path": "./"},
    {"id": 2, "title": "关于", "path": "about/"},
    {"id": 3, "title": "使用指南", "path": "guide/"},
    {"id": 4, "title": "API 参考", "path": "api/"}
  ],
  "page": 1,
  "page_size": 10,
  "total": 4
}
```

| 字段 | 含义 |
| --- | --- |
| `items` | 本页文档条目；没有匹配内容时为空数组 |
| `items[].id` | 文档的整数标识 |
| `items[].title` | 文档显示标题 |
| `items[].path` | 相对于文档网站根路径的页面地址 |
| `page`、`page_size` | 当前页码和每页条数 |
| `total` | 全部匹配条目总数 |

这里的 `path` 相对于文档网站根目录。例如 `guide/` 对应 [使用指南](guide.md)，`./` 对应[首页](index.md)；项目站点的 URL 中还会包含 `/my-docs/` 前缀。

### 空结果示例

本例约定，查询超出已有条目的页码时返回空数组，保留总数。共有四条、每页十条时，请求第二页的演示响应为：

```json
{
  "items": [],
  "page": 2,
  "page_size": 10,
  "total": 4
}
```

### 参数错误示例

例如 `page=0` 时，文档约定返回 `400 Bad Request`：

```json
{
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "page 必须大于或等于 1"
  }
}
```

## 我的接口文档练习体会

整理这个示例时，我把参数范围、成功响应、空结果和错误响应放在同一页，发现这几部分需要相互对应：参数表允许省略页码，示例就应采用默认值；返回列表写了四个条目，`total` 也应是四；翻到没有数据的一页时，响应结构仍应保持一致。

文档中还需要明确实现范围。这一页完成的是接口描述练习，实际网页由 MkDocs 生成。后续如果实现后端，可以把这里的约定作为开发和测试的参考。

| 我核对的项目 | 本例的对应方式 |
| --- | --- |
| 内容与本站有关 | 列表条目对应网站四页 |
| 参数范围明确 | `page >= 1`，`page_size` 为 1 到 100 |
| 返回示例一致 | 四个条目与 `total: 4` 对应 |
| 边界情况有说明 | 提供空结果和无效页码示例 |
| 页面有阅读入口 | 正文和页末均提供本站链接 |
