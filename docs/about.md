# 关于本项目

## 我为什么做这个项目

我使用 GitHub 账号 Ottor1 完成这次文档建站实践。我的学习目标是把 Markdown、Python 虚拟环境和 GitHub 工作流连接起来，理解每一步的输入、输出和检查方法，并留下下次能够照着操作的记录。

这次最具体的收获来自环境选择和下载排错。课程命令中的 `python` 看起来很简单，但电脑上可能存在多个解释器；下载失败时，终端又可能连续打印大量重试信息。把这些实际问题写进文档，有助于我解释每一条命令为什么这样执行。

## 项目目标

本项目用于练习开源软件开发中的文档维护与持续部署。目标是让文档的写作、校验和发布有清楚的分工：在本地编写和检查，在 GitHub 上保存版本，再由工作流生成并发布网站。

网站包含首页、关于、使用指南和 API 参考四页。页面之间使用相对链接，既方便在仓库内阅读，也能由 MkDocs 转换为网站导航。

## 技术组成

| 工具 | 作用 | 项目中的对应内容 |
| --- | --- | --- |
| Markdown | 保存文档正文、表格和代码示例 | `docs/*.md` |
| MkDocs Material | 读取配置并将文档构建成静态页面 | `mkdocs.yml`、`site/` |
| Python 虚拟环境 | 隔离本地依赖，明确使用的解释器 | `.venv/` 或独立 Conda 环境 |
| GitHub Actions | 按工作流完成安装、构建与部署 | `.github/workflows/deploy.yml` |
| GitHub Pages | 托管生成的网站 | 项目网站地址 |

## 文件如何协作

1. `mkdocs.yml` 的 `nav` 定义四页顺序，路径相对于 `docs/`。
2. `requirements.txt` 声明构建时需要安装的 MkDocs 和主题。
3. `python -m mkdocs build --strict` 根据配置生成 `site/`，出现警告时构建失败，便于在发布前发现问题。
4. 工作流把 `site/` 作为 Pages 构建产物上传，部署任务再发布这份产物。
5. `report/` 用于保存实验说明和真实截图，它不在网站的内容目录中。

这次报错中值得关注的信息是下载站点、包名和异常类型：


这些信息说明错误发生在 HTTPS 下载连接阶段。结合后续换源安装和构建成功的结果，可以确认本项目在当前 Python 3.13 环境中能够运行。具体命令见[使用指南](guide.md)。

## 我的实践体会

### 明确解释器，才能解释安装结果

这次让我注意到，创建虚拟环境和使用虚拟环境是两个步骤。安装依赖、运行 MkDocs 时都指向 `.venv` 中的 Python，才能让两者使用同一套包。以后排查 `No module named ...` 一类问题时，我会先查看 `sys.executable` 和 pip 所在路径。

### 读懂日志中的关键位置

面对连续的重试提示，我会先找最后的错误，再看它发生在哪个阶段。本次通过包名、镜像域名和 SSL 错误定位下载连接问题，换源后重新安装并构建，形成了“现象—处理—验证”的记录。

### 用可见变化检查更新

能够打开页面后，我还需要确认这次新增的文字真的出现在目标网站上。因此首页保留了日期和更新说明，后续可与提交记录、Actions 运行和网页截图对应。这样的检查可以帮助我区分本地预览与公开网站的更新结果。

### 让文档服务下一次操作

我把这次实际使用的命令和环境写入指南，下一次维护时就能直接找到安装、构建与预览方法。把 `docs/` 源码、`site/` 生成文件和工作流分开保存，也便于根据失败阶段查找相应位置。
